## Key question 1: What specific coding problems are attributed to Sierra's phone screen, OA, onsite and take-home rounds?

### Takeaway
The recurring, independently corroborated Sierra problems are (a) a multi-part "practical" phone-screen exercise built around a flaky/paginated API whose response must then be transformed (fallback product-ID resolution, or compacting records/messages to a token budget), (b) "split a Markdown document into header-aware chunks under a size limit", (c) "detect circular references between spreadsheet cells" (cycle detection), (d) an interval merge/overlap/gap problem ("Debug View") in the online assessment, (e) a "keyboard object with undo/redo and expanding requirements" OOP design, (f) a debugging round on a small multi-file agent codebase (Python or TypeScript/React) with ~3–6 planted bugs, and (g) a take-home to build a customer-support AI agent (with provided LLM API key) for a fictional company, later presented/extended onsite.

- "Fetch Every Page from a Data API, Then Compact Records to a Token Budget" — COMMUNITY QUESTION BANK, Software Engineer, Technical Screen, Medium, dated Oct 1 2026. Part 1: `fetch_all(fetch_data)` where `fetch_data(cursor)` returns a batch of records (each with a non-negative integer `tokens`) plus next cursor; first call uses `cursor=None`; empty batch = end; return all records in order; discuss repeated cursor, never-empty API, transient failures without losing/duplicating, memory vs streaming. Part 2: `compact(records, trigger=20_000, target=10_000)` — if total tokens exceed trigger, return the longest contiguous run (original order) whose total fits target, else unchanged. Example: `[4000, 3000, 5000, 2000, 1000, 6000, 3000]` totals 24,000; no run of 4 fits; runs of 3 such as `[3000, 5000, 2000]` fit. Follow-ups: incremental maintenance as records are appended; always keep the most recent record; maximize tokens instead of count; summarize excluded records. — [PracHub](https://prachub.com/interview-questions/fetch-every-page-from-a-data-api-then-compact-records-to-a-token-budget)

Part 1: assemble one ordered list across pages (termination, order, empty pages, transient failures, repeated cursor, eager vs lazy). Part 2: when total tokens exceed the limit, drop oldest messages until it fits; must be cheap enough to run after every message (running total, O(1) front removal via deque; edge cases: single oversized message, empty history, messages that must be kept). Follow-ups: summarize old messages and budget the summary's tokens; keep tool calls and results together; avoid duplicates/gaps when new messages arrive mid-pagination; test without a live service. FIRST-HAND, Software Engineer OA, posted 2025-11-25 ("problems were not hard"). — [1point3acres thread 1155857](https://www.1point3acres.com/interview/thread/1155857); [t.me re-post](https://t.me/s/usinterview?q=%23sierra)

Part 2 — ignoring text, return `(any_overlap, any_gap)` between earliest start and latest end; empty → `(False, False)`. Constraints n ≤ 200,000, 0 ≤ start < end ≤ 1e9. — [PracHub](https://prachub.com/interview-questions/process-time-intervals-and-detect-overlaps-gaps)

## Key question 2: What is the loop structure and what does each round test?

### Takeaway
Two loop generations coexist in the reports. The older/Agent-Engineer loop (2025 → at least Oct 2026 in candidate reports) is: 30-min recruiter call → 45–60-min practical coding screen (CoderPad, no AI) → take-home agent build → in-person onsite of three ~60-min rounds (debugging, take-home presentation + extension, hiring-manager behavioral). Sierra's official April 2026 "AI-native" loop for product SWEs replaces the coding screen with system design and replaces coding/algorithms onsites with a Plan → 2-hour AI-assisted Build → Review session, plus a debugging pilot on a colleague's draft PR.

### Cited Findings

**Official (Sierra blog, Apr 22 2026, authors Vijay Iyengar, Arya Asemanfar, Angie Wang)**
- Old loop: two coding interviews, algorithms and system design interviews, culture-fit interview, reference checks, plus a coding phone screen "in an online editor, with no AI allowed." — [Sierra blog](https://sierra.ai/blog/the-ai-native-interview)
- New loop: AI-native onsite "replaces coding and algorithms interviews" — Plan (candidate drives ideation of a product in their own domain), Build (interviewer leaves; 2 hours; any AI tools/frameworks; may pivot or cut scope), Review (demo; discuss product flows; code review of data model, abstractions, extensibility; path to production; how AI was used). A system design interview "replaces the coding phone screen, focused on taking work to production at scale." Debugging pilot: medium-sized codebase + colleague's draft PR with a cross-cutting feature; AI level "TBD". Candidates get advance guidance that it is OK to cut scope and skip boilerplate (CRUD, auth). Signals: agency, judgment, initiative, ownership, system understanding, product thinking; criteria independent of what is built; interviews run in pairs; format adapted for infrastructure roles. — [Sierra blog](https://sierra.ai/blog/the-ai-native-interview); summarized by [four-leaf.ai](https://four-leaf.ai/blog/sierra-interview-process) and [Bret Taylor on X](https://x.com/btaylor/status/2046996207898366248)
- Careers page: "Since we work in person, interviews take place at one of our offices." and "we'll evaluate not only your capabilities, but also how well you align with our values." OFFICIAL. — [Sierra careers](https://sierra.ai/careers)

## Key question 3: Are the problems LeetCode-style or practical multi-part problems?

### Takeaway
Predominantly practical and multi-part: nearly every first-hand coding report describes a scenario (API client, markdown document, log intervals, conversation history, spreadsheet model) that grows in stages, with the interviewer layering requirements onto existing code; classic LeetCode items (cycle detection, grid word search, sliding window) appear mainly in 2025 Agent Engineer / new-grad reports.

### Cited Findings
- "Practical, multi-part problem that builds on itself… Each new requirement is added on top of your existing code, testing whether you write extensible code from the start." FIRST-HAND. — [Gaijineer](https://gaijineer.co/sierra-software-engineer-agent-interview-experience)
- "Three parts, with only 30 minutes for coding… Part 1 was simple: repeatedly fetch data from an API until no more data is returned." FIRST-HAND. — [t.me/s/usinterview](https://t.me/s/usinterview?q=%23sierra)
- "first part connects to an API using a provided client. The second and third parts transform the response object, roughly LeetCode Easy and Medium difficulty." FIRST-HAND. — [Blind](https://www.teamblind.com/post/sierra-ai-hiring-and-future-peb5ne2v)
- The APX candidate: "Prep less for classic LeetCode and more for hands-on debugging and reading unfamiliar code." FIRST-HAND. — [Aced APX](https://www.aced.io/experiences/sierra-ai-interview-67fe22)
- Counter-example: Agent Engineer screen c. 2025 was "LeetCode-style" cycle detection; advice "Prepare graph and tree LeetCode problems, since the screen was similar." FIRST-HAND. — [Aced Agent Engineer](https://www.aced.io/experiences/sierra-ai-machine-learning-engineer-interview-8549fc)
- Glassdoor snippet: "a standard DSA LC question" in the technical interview. FIRST-HAND origin. — [Glassdoor](https://www.glassdoor.co.in/Interview/Sierra-Software-Engineer-Interview-Questions-EI_IE10032095.0,6_KO7,24.htm)
- PracHub's two Oct-2026 screen problems are each two+ parts (fetch/paginate, then compact) with follow-ups on incremental maintenance and summarization. COMMUNITY QUESTION BANK. — [PracHub fetch/compact](https://prachub.com/interview-questions/fetch-every-page-from-a-data-api-then-compact-records-to-a-token-budget); [PracHub conversation history](https://prachub.com/interview-questions/conversation-agent-history-paginated-fetching-then-token-limit-compaction)

- Official position: Sierra explicitly removed coding/algorithms interviews because "vibe-coding an app is easy" (as quoted by vibeengines) and now evaluates data model, abstractions and extensibility of a built artefact. — [Sierra blog](https://sierra.ai/blog/the-ai-native-interview); [vibeengines](https://vibeengines.com/handbook/fde-interview-sierra)

### Inferences
- Sierra's problems are mostly "simulate a small system / implement a class progressively" in style; the hard part is time pressure (30 min coding for 3 parts) and edge-case rigor rather than algorithmic novelty. The sorting/greedy/deque techniques needed are LeetCode-easy/medium.
- Interviewers consistently probe trade-offs ("why this over alternatives", complexity, what to do with oversized items/failures), so narrating clarifying questions is scored.

### Gaps

## Key question 5: What do prep sites recommend practicing for Sierra, and on what basis?

### Takeaway
Advice converges on: practice API-driven, multi-part Python/TypeScript exercises (pagination, retries, JSON wrangling, extensible classes), rehearse reading/debugging unfamiliar agent code and explaining customer impact, build a tool-calling agent loop without a framework, and prepare STAR stories for Sierra's five values — the first-hand accounts ground the first three; vendor guides add generic system-design and "AI-native build" drills that are author-constructed, not reported prompts.

### Cited Findings
- First-hand advice (Gaijineer): get comfortable with Python or TypeScript; "practice practical coding, class design, and writing extensible code that handles changing requirements"; be ready to discuss data-structure trade-offs; "don't rely only on memorizing algorithms." — [Gaijineer](https://gaijineer.co/sierra-software-engineer-agent-interview-experience)
- First-hand advice (Aced Agent Engineer): graph/tree LeetCode for the screen; learn TypeScript + basic React; for the take-home "build an agent without hiding behind a big framework, understand OpenAI tool calling, and be ready to discuss metrics, observability, and feature trade-offs." — [Aced Agent Engineer](https://www.aced.io/experiences/sierra-ai-machine-learning-engineer-interview-8549fc)
- First-hand advice (Aced APX): "Prep less for classic LeetCode and more for hands-on debugging and reading unfamiliar code. Practice explaining the customer impact of bugs, not just the fix." — [Aced APX](https://www.aced.io/experiences/sierra-ai-interview-67fe22)
- First-hand advice (Aced L5): "Practice practical coding: API calls, error handling, retries, and pagination. Practice wrangling JSON data." — [Aced L5](https://www.aced.io/experiences/sierra-ai-senior-ai-engineer-interview-087f4e)
- First-hand advice (Aced FDE): go deep on your own technical projects; communicate clearly (front-facing role); know Sierra's values. — [Aced FDE](https://www.aced.io/experiences/sierra-ai-forward-deployed-engineer-interview-99c71f)
- Sierra's values used in behavioral rounds: Trust, Customer Obsession, Craftsmanship, (Competitive) Intensity, Family — cited by Aced guide, Extern, DesignGurus (secondary; from Sierra postings). — [Aced guide](https://www.aced.io/guides/sierra-agent-engineer-interview); [Extern](https://www.extern.com/post/sierra-internship-guide); [DesignGurus](https://www.designgurus.io/answers/detail/what-is-the-sierra-interview-process-like-round-by-round)
