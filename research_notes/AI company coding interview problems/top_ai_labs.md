## Key Question 1: What exact coding problems (with parts) did these companies ask in the last year?

### Takeaway
The best-documented loops (Anthropic, OpenAI, Databricks, xAI) all converge on "implement a small stateful system, then extend it" problems rather than LeetCode puzzles: Anthropic's 90-minute 4-level CodeSignal build (in-memory KV database / banking ledger / file storage), OpenAI's 5-part grid infection simulation and expiring-credits ledger, Databricks' CIDR firewall / snapshot-iterator / streaming RLE / generalized tic-tac-toe set, and xAI's KV store with nested transactions and stateful iterator. Figma, Harvey, Scale, Ramp and Cursor have fewer concrete reports; the problem shapes there are product-framed (tokenizer well-formedness at Figma, RAG notebook at Harvey, evolving card-game spec at Scale, double-entry ledger at Ramp, text-buffer/edit-application at Cursor).

**Problem A1 - CodeSignal OA: progressive in-memory database (the most-reported Anthropic problem).** 90 minutes, one problem in 4 levels, each level's tests must pass to unlock the next. Linkjob author's account (dated 2025-09-05, **[OLD by 2 months]**, vendor post, partly "compiled from others"):
  - Level 1: in-memory store of keyed records with string fields; SET, GET, DELETE (DELETE returns "true"/"false").
  - Level 2: SCAN and SCAN_BY_PREFIX; output fields sorted alphabetically formatted `field(value)`.
  - Level 3: timestamped variants SET_AT, GET_AT, DELETE_AT, SCAN_AT, SCAN_BY_PREFIX_AT, plus SET_AT_WITH_TTL; validity is half-open [timestamp, timestamp+ttl); backward compatibility with earlier levels required.
  - Level 4: COMPRESS_FILE / DECOMPRESS_FILE checking user existence, ownership, storage capacity, file existence (example also used ADD_USER, ADD_FILE_BY, GET_FILE_SIZE, COPY_FILE).
  - Author: each function "wasn't difficult on its own" but time "a bit tight". [1st-ish, vendor] — [Linkjob](https://www.linkjob.ai/interview-questions/anthropic-software-engineer-interview/)

**Problem O2 - Expiring GPU credits ledger (technical screen, Medium, "Very high frequency").** PracHub statement (updated Apr 30, 2026): multi-user ledger; each `add` creates a lot with its own expiry; lot usable iff `timestamp < expiry_time`; subtract consumes earliest-expiring valid lots first (partial lot consumption allowed); failed subtract leaves state unchanged; subtract/balance timestamps non-decreasing.
  - Part 1: implement `add_credit`, `subtract`, `get_balance` and write tests for (a) single lot added and spent, (b) spending across lots with different expiries, (c) spending after a lot expires, (d) insufficient-balance failure leaving state unchanged, (e) expiry boundary.
  - Part 2 (editor version): `solution(operations)` processing tuples `('add', user, amount, expiry)`, `('subtract', user, amount, ts)` -> True/False, `('balance', user, ts)` -> `(total, [(amount, expiry), ...])` sorted by expiry; empty -> `(0, [])`. Constraints: up to 20,000 ops, amounts/times up to 1e9. Example: `[('add','u1',50,10), ('balance','u1',5), ('subtract','u1',20,6), ('balance','u1',6)]` -> `[(50,[(50,10)]), True, (30,[(30,10)])]`.
  - Part 3 (follow-up): time/space complexity, reaching O(log n) per op, how to persist and restore ledger state. [2nd] — [PracHub GPU credits](https://prachub.com/coding-questions/implement-an-expiring-gpu-credits-ledger)
  - Harder variants: "GPU Credit Ledger with Out-of-Order Events" (events arrive late; queries consider only events up to query time) and retroactive grant revocation — [1point3acres list](https://www.1point3acres.com/interview/problems/company/openai); [search summary](https://www.1point3acres.com/interview/post/7100064)

### Inferences
- Anthropic's live screens appear to draw from a small rotating pool (web crawler -> concurrent; stack samples -> trace events; Pillow image pipeline -> parallel; LRU cache variants; tokenizer), each with a "now make it concurrent / now handle streaming" second act; the OA is a different, test-gated progressive-levels format (CodeSignal Industry Coding Framework style). PracHub listing dates (Mar-Sep 2026) and Hack2hire's April 2026 report set put these squarely inside the Nov 2025-Nov 2026 window.
- OpenAI's infection problem is reused across SWE/MLE/RE screens and onsites with different part orderings; the three most stable parts are (1) spread with simultaneous update and day count, (2) permanent immunity, (3) recovery/immunity after D days; parts 4-5 vary (expiring immunity, death threshold, burn intervention). The GPU credits ledger (lots with expiry, earliest-expiring-first consumption) is the second recurring stateful-class problem and has a harder "out-of-order events / event replay" second version.
- Databricks' pool is unusually stable (CIDR, RLE/streaming codec, commute grid, snapshot iterator, generalized tic-tac-toe, Fibonacci tree) and leans algorithmic with an API-design flavor; its "concurrency round in pseudocode with ever-added constraints" is the closest thing to a multi-part escalation.
- Scale, Ramp, Figma, Harvey have moved toward product-domain framing (card game spec, ledger, tokenizer/rich-text, RAG notebook) where the "parts" are requirement changes rather than algorithmic tightening.

## Key Question 2: Which problems are multi-part and how do the parts escalate?

### Takeaway
Three escalation patterns recur: (a) **test-gated levels** that add operations to the same data model (Anthropic OA: CRUD -> scans -> timestamps/TTL -> files/users; OpenAI OA/onsite "Multiple sub-problems progressing in difficulty"), (b) **rule accretion in a simulation** (OpenAI infection: spread -> immunity -> recovery -> expiring immunity -> death/burn; Scale card game: new rules, win conditions, card types), and (c) **non-functional escalation on a finished base** (Anthropic/Databricks: make it concurrent, make it streaming, bound the memory, make it crash-resilient, add TTL; xAI: nest the transactions, span many iterators, add compound/payload-aware limits).

### Cited Findings
- Anthropic OA levels (SET/GET/DELETE -> SCAN/SCAN_BY_PREFIX -> *_AT timestamped ops + SET_AT_WITH_TTL with half-open validity and backward compatibility -> COMPRESS_FILE/DECOMPRESS_FILE with user/capacity checks); "I had to complete the previous level and pass all unit tests to unlock the next one." — [Linkjob](https://www.linkjob.ai/interview-questions/anthropic-software-engineer-interview/); scoring weighted to later levels, "Three clean levels beat four broken ones" — [Calibrd](https://www.calibrd.com/interview-prep/anthropic-interview); Hello Interview: "Implement initial operations, then extend the same code as new behavior is added while keeping earlier tests passing." — [Hello Interview](https://www.hellointerview.com/guides/anthropic/swe)

## Key Question 4: Which problem families recur across labs?

### Takeaway
Six families account for most reported problems: (1) in-memory KV store / database with transactions, versioning/time-travel, TTL and persistence (Anthropic, OpenAI, xAI, Databricks snapshot iterator); (2) LRU/cache with eviction, TTL, thread-safety, crash-resilience (Anthropic, Databricks, xAI, Harvey, Figma); (3) ledgers and credit systems with expiry/idempotency (OpenAI GPU credits, Anthropic banking system, Ramp double-entry ledger, Databricks referral credits); (4) grid simulations / game rules with accreting rules (OpenAI infection, Anthropic threshold infection, Databricks tic-tac-toe, Scale card game, OpenAI monster battle/poker hands); (5) rate limiters and sliding-window counters (OpenAI, xAI, Ramp, Databricks hit counter, OpenAI chat-event aggregation); (6) task queues/schedulers with dependencies, DLQ, cooldowns (OpenAI, Scale, Anthropic task manager OA, Databricks job scheduler design). Concurrency-on-top (web crawler, image pipeline, logger) is Anthropic/Databricks-specific; tokenizers and LLM-codebase tasks appear at Anthropic and xAI; CIDR/IP appears at Databricks and OpenAI.
