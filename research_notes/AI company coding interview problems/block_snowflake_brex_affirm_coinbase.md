# Coding interviews at Block, Snowflake, Brex, Affirm, Coinbase (AI-adjacent SWE roles), Nov 2025 - Nov 2026

Research date: 2026-11-12. Scope: reconstruct the coding problems (especially multi-part / progressive ones), formats, AI-tool policies and process for the named roles. Reports dated before Nov 2025 are included only where they are the sole evidence for a pattern and are explicitly flagged OLD.

Confidence labels used below:
- FIRST-HAND = a candidate's own account (Blind/1point3acres/PracHub experience post/Taro/Screna/FrontendLead).
- OFFICIAL = company's own blog/careers page/CTO interview.
- SECOND-HAND = prep-site guide or question bank that paraphrases candidate reports without dating them (PracHub guide pages, Nyrion, TechPrep, CareerClimb, Lodely, etc.). Treat problem wording from these as a reconstruction.
- INFERRED = my inference.

Access notes: Glassdoor (all country mirrors), the Coinbase blog, CodeSignal support and Snowflake careers blog body returned 403 to fetch; 1point3acres thread bodies are login-walled (summaries only). Where a Glassdoor report is cited, the text comes from the search-engine snippet of that page, not the page itself.

## Key question 1: What exact coding problems (with parts) did each company ask in the last year?

### Takeaway
Coinbase has the richest and most recent first-hand record: a 4-level CodeSignal pre-screen (banking system / in-memory DB with TTL+backup variants, now sometimes an AI-assisted game task), then onsite rounds that are explicitly multi-part (block mining Part 1/Part 2; a 4-sub-task AI-assisted cursor-pagination repo exercise; small implementation tasks with escalating follow-ups). Snowflake's phone screen is confirmed to be a 60-minute design-and-extend problem (tiered rate limiter with four follow-ups; web-crawler shortest-clicks then shortest-path; Throne Inheritance variant; ACL; Connect-Four check; logger library with multiple sinks). Block has shifted to a Kotlin "Live AI Build" round with a coding agent plus CoderPad pair-programming with 2-3 follow-ups. Brex's CTO says the loop was rebuilt around an onsite project that "requires agentic coding". Affirm remains HackerRank-practical (text parsing/aggregation, fix-then-rebuild a Python pipeline, O(1) get/put/delete/random data structure with a relaxed-then-tightened delete bound).

### Cited Findings

#### Coinbase

Process (OFFICIAL + FIRST-HAND):
- Coinbase published "Interviewing Engineers in the AI Era: Lessons from a Year of Rebuilding" on 2026-07-13. Three phases: a frontend pilot with AI-enabled questions (H2 2025), expansion to backend with repository-based debugging tasks (Jan 2026), company-wide "AI Fluency" rollout in March 2026. Motivation: AI-generated code "crossed 50% of merged code in Q4 2025" (from 5.7% in Q1 2025); internal analysis found an "84% correlation between two interview rounds" (redundant signal). Current loop signals: repo-based coding and debugging (live), system design with AI (early testing), leadership/behavioral with AI questions (live). Quarterly refresh of questions because of the "half-life problem"; 45/90-day pulse surveys check whether interview performance predicts on-the-job AI fluency; "adds no rounds". — [Coinbase blog (403 on direct fetch; summarized via daily.dev)](https://www.coinbase.com/blog/interviewing-engineers-in-the-ai-era-lessons-from-a-year-of-rebuilding), [daily.dev summary](https://daily.dev/posts/interviewing-engineers-in-the-ai-era-lessons-from-a-year-of-rebuilding-gcnp8fq6t), [HN thread 2026-08-03, 65 comments, no Coinbase insiders describing rounds](https://news.ycombinator.com/item?id=49162299)

  - R1 cooldown scheduling: "Given an ordered task list and cooldown n, find the minimum number of days to finish. Identical task types must be at least n days apart, and idle days are allowed." Follow-ups: n = 0; empty list (return 0); string task IDs; "where a future maintainer would most likely introduce a bug" (candidate pointed to the "+1"). Interviewer valued maintainability over speed of idea generation.
  - R2 moving average: "Build a sliding-window average tracker with window size k. It averages over fewer than k values until the window fills." Candidate used circular array + running sum (O(1)/op, O(k) space); added tests for partial/full/rolled-over windows, k = 1, all-negative; validated k > 0; discussed floating-point drift (periodic recomputation). Follow-up: concurrency (locking vs atomics; document thread-safety guarantees).

Two ordered sets (top-k and rest) rebalanced on insert/remove, hash map user -> score. Candidate initially missed stale data on score update; interviewer prompted. Tests focused on removing a user at the top-k boundary.
  - R4 behavioral (no coding): code you are proud of; a production incident; when tests are necessary; resolving a code-review disagreement. Candidate's inferred rubric: correct, maintainable code others can change safely; edge cases and meaningful tests; precision/concurrency/input validation; proactively surfacing risks.

#### Snowflake

- FIRST-HAND, Aug 2026 technical phone screen (SWE, rejected): one hour, Python in CoderPad, "AI use was allowed". Recruiter framing: the round looks at "how you ask about requirements, how you test, and how you debug". Problem: build a tiered rate limiting service; clients belong to tiers (free, pro, enterprise) each with its own limit; tier limits updatable at runtime without restart; a request carries a client id, enforce that tier's limit and reject over-limit; verbal addition: clients with no tier / broken config fall back to a global default policy ("Default deny or default approve are both fine"). Follow-ups in order: (1) why this algorithm, pros/cons of alternatives; (2) add tests; (3) real clock makes refill hard to test, how do you handle time (mock clock vs sleep); (4) single-instance in-memory state, how to evolve to a distributed cluster. Candidate ran out of time before (4) and attributes the rejection to that: "Everyone should watch their time on this question." Pitfalls flagged: on a limit increase capacity is only an upper bound (tokens don't jump); refill = elapsed x rate, not x capacity. — [PracHub experience, published 2026-10-03](https://prachub.com/interview-experiences/snowflake-software-engineer-interview-experience-rate-limiter-in-coderpad-ran-out-of-time-before-the-distributed-follow-up)
