# Multi-part ("progressive" / "staged" / Industry Coding Framework) interview problems: formats and problem families, Nov 2025 – Nov 2026

Research date: 2026-11-12. Scope: cross-company landscape of multi-part coding interview problems at AI labs and high-paying tech companies, for a pytest-judged timed mock-interview platform.

Source-dating convention used below:
- **[in-window]** = source dated Nov 2025 or later (counts for "who uses it now").
- **[pre-window]** = older source, cited only for a format's origin or canonical spec.
- **[first-hand]** = candidate or interviewer reporting their own experience. **[second-hand]** = prep site / aggregator / compilation.
- **[reconstruction]** = my own concretisation of a family into a pytest-able spec, not something a source described.

---

## Key Question 1: What are the most-reported multi-part problem families, with canonical part sequences?

### Takeaway
Roughly a dozen families recur. The four best-evidenced in the last year are all CodeSignal Industry Coding Assessment (ICA) "one project, four levels" problems: (1) cloud/file storage with capacity → prefix search → TTL → rollback/backup-restore; (2) banking system with accounts/transfers → top-N spenders → scheduled/two-phase payments → merge accounts; (3) in-memory key-value database with SET/GET/DELETE → scans/filters → TTL → persistence/backup/transactions; (4) task management with CRUD → search/priority sort → user quotas + expiring assignments → complete/overdue. Live (CoderPad/CodeSignal-shared) multi-part rounds at AI labs add: dependency-aware task graph (Perplexity, official), in-memory SQL and spreadsheet-with-cycles (OpenAI), Unix-path/file-system simulators (OpenAI, Perplexity, Anthropic), interval/scheduling follow-ups (Scale), flaky-API/undo-redo OOP (Sierra), and LLM agent-loop/tool-dispatch (Cohere and AI-engineer loops). Rate limiter, LRU+TTL cache, tokenizer/BPE and web crawler are reported but mostly second-hand. No in-window sources at all were found for event-stream merging, chat-history compaction, markdown chunking, or a dependency-resolver/package-manager with concrete levels.

### Cited Findings

#### Family 1 — Cloud / file storage service (CodeSignal's own canonical ICA example)
- CodeSignal's framework brief gives this as *the* worked example. Level 1: `FILE_UPLOAD(file_name, size)` (throws if the name already exists), `FILE_GET(file_name)` (returns size or nothing), `FILE_COPY(source, dest)` (throws if source missing; overwrites dest). Level 2: `FILE_SEARCH(prefix)` — "Find top 10 files starting with the provided prefix. Order results by their size in descending order, and in case of a tie by file name." Level 3: timestamped variants `FILE_UPLOAD_AT(timestamp, file_name, file_size[, ttl])`, `FILE_GET_AT`, `FILE_COPY_AT`, `FILE_SEARCH_AT` — "no ttl means lifetime being infinite", search "should only include files that are still 'alive'". Level 4: `ROLLBACK(timestamp)` — "Rollback the state of the file storage to the state specified in the timestamp. All ttls should be recalculated accordingly." Instructions: "Please, do not change the existing method signatures." Partial credit per test passed. — [CodeSignal Industry Coding Skills Evaluation Framework technical brief (PDF, created 2024-09-11)](https://discover.codesignal.com/rs/659-AFH-023/images/Industry-Coding-Skills-Evaluation-Framework-CodeSignal-Skills-Evaluation-Lab-Short.pdf) **[pre-window, origin]**
- The community mock repo (PaulLockett) implements the same file-storage theme with a Python test file per level; a GitHub issue (opened Sep 14 2025, comments to Feb 14 2026) documents that the mock's Level-4 tests expect a *non-destructive* rollback (files created after the timestamp remain: "found at [Update1.txt, Update1Copy.txt, Update2.txt]") while the spec text implies version-control-style removal — commenters agreed tests and requirements do not match. — [GitHub issue #16](https://github.com/PaulLockett/CodeSignal_Practice_Industry_Coding_Framework/issues/16) **[in-window comments, first-hand practice reports]**; repo: [PaulLockett/CodeSignal_Practice_Industry_Coding_Framework](https://github.com/PaulLockett/CodeSignal_Practice_Industry_Coding_Framework)
- Ramp 2026 OA debrief (Medium, fetch blocked 403; details from search snippet only): Level 4 adds snapshot/restore — `restore_user` "restores to the latest backup, or wipes the user's files if there's no backup"; restore "leaves the capacity limit unchanged and only affects used space"; "Files whose names are now held by another user are skipped." — [Ramp 2026 OA Debrief: The CodeSignal Cloud Storage Problem, All Four Levels](https://medium.com/@yourxc943/ramp-2026-oa-debrief-the-codesignal-cloud-storage-problem-all-four-levels-70333d2810fe) **[in-window, first-hand, snippet-only]**
- A second Ramp 2026 report (published Sep 29 2026) says the author "cleared all four levels before time ran out", finished Level 1 "in under 5 minutes", 90-minute cap, and that there is "no official Ramp threshold" on the 200–600 scale. — [InterviewFox Ramp CodeSignal OA guide](https://interviewfox.ai/interview-questions/ramp-codesignal-oa-guide/) **[in-window, first-hand but thin on spec]**
- Meta OA (2026 prep guides): "about 90 minutes on CodeSignal, with camera and microphone monitoring", "a problem with four progressive stages — think building out a simplified in-memory database or a cloud file storage system"; "most candidates don't finish all four stages, and that's expected." A separate Meta review lists Level 4 as *file compression* rather than rollback. — [copilotinterview Meta OA](https://copilotinterview.com/blog/meta-online-assessment); [oavoservice Meta OA cloud storage](https://oavoservice.com/en/articles/meta-oa-cloud-storage-system) **[in-window, second-hand]**
- Airbnb candidates report "a four-level cloud-storage ICA" alongside a task-management variant. — [PracHub Airbnb ICA guide, Sep 3 2026](https://prachub.com/resources/airbnb-codesignal-industry-coding-assessment-2027-four-levels-90-minutes-scoring-and-what-comes-next) **[in-window, second-hand]**
- Companies in-window reported using this family: Ramp, Meta, Airbnb. (Variants also appear in Anthropic reports as "file deduplicator" / "file system".)

#### Family 2 — Banking system (ICA)
- **Meta (interview Sep 2025, published Aug 25 2026) [first-hand]**: L1 `createAccount(timestamp, customerId)`, `deposit(timestamp, customerId, amount) -> int`, `pay(timestamp, source, target, amount) -> int`. L2: top-N accounts by activity (sum of deposit + pay amounts). L3: `transfer(timestamp, targetAccountId, amount) -> transferId` holds money from source; `accept(timestamp, accountId, transferId) -> bool`; transfers expire — if expired on accept, held money returns to source; a successful accept must add to activity totals; deposit/pay must return correct values after expiry. L4: `mergeCustomers(oldId, newId)` preserving balances and histories (not attempted). L1+L2 took ~15 minutes; the rest went to debugging L3 against "a long test case with 10 accounts and many operations." — [PracHub Meta bank system experience](https://prachub.com/interview-experiences/meta-software-engineer-interview-experience-three-of-four-levels-on-the-bank-system-question)
- **Airbnb (Sep 2026) [first-hand]**: L1 `create_account(timestamp, account_id)`, `deposit(timestamp, account_id, amount)`, `transfer(timestamp, source, target, amount)`. L2 `top_spenders(timestamp, n)` ranked by total outgoing. L3 scheduled payments — "the biggest trap" is timestamp execution order: "Before handling any later operation, the system must first process scheduled payments that should have executed before that timestamp. Storing a record at schedule time is not enough." L4 merge accounts keeping both balances and histories. Score 440; author assumed fail. — [PracHub Airbnb banking OA, 440 points](https://prachub.com/interview-experiences/airbnb-software-engineer-interview-experience-four-level-banking-system-oa-stuck-on-level-3-at-440-points)
- **Circle OA spec (last updated Jun 26 2026) [second-hand but fully specified]**: string-token operations with unique strictly increasing ms timestamps; `CREATE_ACCOUNT -> 'true'/'false'`; `DEPOSIT -> new balance as string or ''`; `TRANSFER -> source's new balance or ''` (missing account, self-transfer, insufficient funds); `TOP_SPENDERS ts n -> "id(amount), id(amount)"` sorted outgoing desc then id asc, `''` if no accounts; `SCHEDULE_PAYMENT ts account amount delay -> 'paymentN'` (global counter), `CANCEL_PAYMENT -> 'true'` only if PENDING and owned, `GET_PAYMENT_STATUS -> PENDING|PAID|CANCELED|''`; processing rule: before each operation, PENDING payments with executeAt <= ts run in scheduling order, execute only if balance covers, add to outgoing total; payment due at exactly ts runs when that ts's operation is processed; `MERGE_ACCOUNTS ts a1 a2 -> 'true'/'false'` — a1 gets summed balance and outgoing total, a2's PENDING payments reassigned, a2 removed. The page notes an internal inconsistency (hint says unaffordable payment still becomes PAID). — [PracHub: Implement a simplified multi-level banking system](https://prachub.com/coding-questions/implement-a-simplified-multi-level-banking-system)
- Dropbox variant: L3 scheduled payments *with cashback*, L4 merge accounts "retaining both accounts' balance and transaction histories". — [LeetCode Discuss Dropbox OA](https://leetcode.com/discuss/interview-experience/5121903/) **[undated in my results; likely pre-window]**
- Anthropic's take-home is described as "Bank with multiple transaction types ... starts with a general spec and gets more complex across levels. Passing all tests at one level unlocks the next." — [interviewing.io Anthropic guide, 2026](https://interviewing.io/anthropic-interview-questions) **[in-window, second-hand from engineer conversations]**; a 1point3acres thread title reports an Anthropic internship "Pre-Screen Bank System Assessment" — [1point3acres thread 1125621](https://www.1point3acres.com/interview/thread/1125621) (login-walled).
- Companies in-window: Meta, Airbnb, Circle, Anthropic (and Dropbox historically).

#### Family 6 — Dependency-aware to-do list / task graph (live, official)
- Perplexity publishes the exercise it used "throughout much of 2025 and 2026". Data model: `TaskStatus` IntEnum BLOCKED=1, READY_TO_EXECUTE=2, IN_PROGRESS=3, SUCCEEDED=4 (terminal), FAILED=5 (terminal); `Task(task_id, description, status)`. **Part 2** (core): `add_task(description) -> Task` with unique increasing int IDs, initial READY_TO_EXECUTE; `get_task(id) -> Task | None`; `change_task_status(id, new_status) -> bool`, False if unknown id, current status terminal, or new status not strictly higher. **Part 3**: `add_task(description, dependency_ids=None)` — starts READY if no deps or all SUCCEEDED, else BLOCKED; after every update cascade: BLOCKED task whose direct deps all SUCCEEDED → READY; BLOCKED task depending directly or indirectly on a newly FAILED task → FAILED; "transitions must be efficient". **Part 4**: `render_for_llm() -> str` listing id, status, description, dependencies for all tasks (test only checks descriptions appear). Part 1 is reading/signing the integrity agreement. — [Perplexity hands-on coding example: Todo list](https://interviewresources.perplexity.ai/hands-on-coding/examples/todo-list/) **[in-window, first-party]**
- Format: 30–60 min, Python strongly recommended, shared CodeSignal session, full-screen share on Meet; after each part "you and the interviewer verify the solution together before moving on"; "Solving all parts is not required for a positive evaluation." — [Perplexity hands-on coding format](https://interviewresources.perplexity.ai/hands-on-coding/) **[first-party]**

### Inferences
- The ICA families share one skeleton the platform can template: Level 1 = CRUD with string/int returns and explicit failure values (`''`, `false`, exception); Level 2 = a ranked/filtered report with a deterministic tiebreak (size desc then name; outgoing desc then id asc; priority sort); Level 3 = *time* enters (timestamps on every op, TTL/expiry, scheduled/held transactions processed lazily before each op); Level 4 = a state-rewriting operation that must respect everything before it (rollback/restore, merge, version rollback, overdue report). Pytest judges should test the L3 ordering traps explicitly (operation at exactly expiry time; scheduled payment due before a later op; expired transfer accepted) because three first-hand reports name those as where they lost time.
- **[reconstruction]** A pytest-ready "storage" spec consistent with the sources: capacity per user (upload fails when over limit), duplicate name → error, `search(prefix)` top-10 by size desc then name asc, `*_at(ts, ..., ttl)` where alive iff `upload_ts + ttl > ts` (boundary semantics must be pinned in tests), `rollback(ts)` restoring state as of ts with remaining TTLs recomputed relative to ts, `backup(user)`/`restore(user)` where restore skips names now owned by others and leaves capacity unchanged. State rollback destructiveness explicitly in the problem statement; the community mock shows tests and prose diverging on exactly this.
- Live multi-part rounds at labs are shorter (30–60 min, 3–4 parts) and the interviewer "verifies each part together" before unlocking the next; ICA is 90 min, four (sometimes five or six) levels, tests visible, unlock-on-pass. Both reward not finishing cleanly over finishing sloppily.
- The "agent loop / LLM-aware" family is still thin on first-hand reports; the strongest evidence of LLM-flavoured content is Perplexity's `render_for_llm` part and Cohere's LLM-call replacement task, both of which are mostly ordinary stateful-code problems with an LLM-shaped surface.

### Gaps
- No in-window source found for: event-stream merging as a staged problem, chat-history compaction, markdown/document chunking, dependency resolver / package manager with concrete levels, tokenizer/BPE beyond a one-line Mistral mention, inventory/order system beyond Robinhood fractional shares.
- Exact per-level test counts and point weights for ICA problems are not published; the 520/600 and "3 of 4 levels" thresholds are coaching claims (Anthropic) and "no official threshold" (Ramp).
- Ramp cloud-storage and Anthropic in-memory DB first-hand write-ups were paywalled/403 (Medium, 1point3acres); only snippets were captured.
- Level mapping for Anthropic's banking and file-system variants and the content of stages 5–6 are not described anywhere I found.

## Key Question 2: How exactly does the CodeSignal Industry Coding Framework structure its 4 levels and 90 minutes, and who used it in the last year?

### Takeaway
CodeSignal's own brief defines one language-agnostic project with four progressive levels, a 90-minute maximum, scores 200–600, partial credit per test, and explicit per-level time/LOC targets (10–15 min / 20–30 min / 30–60 min / 30–60 min; 15–20 → 110–160 cumulative LOC) that deliberately exceed the cap. In-window reports place it at Meta, Airbnb, Ramp, Anthropic (now 6 stages for some), Circle, Robinhood, eBay and (per prep sites) Instacart, with Perplexity and Anthropic also using CodeSignal shared sessions for live multi-part rounds.

### Cited Findings
- "Each evaluation contains 1 language-agnostic, project-based task with 4 progressive levels. ### Inferences
- A faithful ICA mock should: show the current level's tests, gate the next level on passing, keep a 90-minute wall clock, award per-test partial credit mapped onto 200–600, and expect most candidates to finish 2–3 levels. Realistic pacing targets for a mock: L1 by 15 min, L2 by 30–40 min, L3 by ~75 min, L4 whatever remains.
- The LOC targets (15–20 → 110–160) are a useful sanity check on problem size when authoring: a complete Level-4 Python solution should land around 110–160 lines.

## Key Question 3: Which companies now allow AI tools in coding interviews, and how do their problems change?

### Takeaway
In the last year the AI-allowed round moved from startup experiment to a named round at Meta (60-min CoderPad AI-enabled round, pilot Oct 2025, 2026 rollout), DoorDash (60-min own-machine session, Mar 2026), Google (Gemini in a "code comprehension" round, H2 2026 pilot), Sierra (2-hour Build with any tools, Apr 2026), Canva (since mid-2025), and pilots at Anthropic; Cohere, Glean, Cursor, Shopify, Stripe and many YC startups are reported permissive. Problems get bigger and more realistic (multi-file starter codebases, 120+ line features, ambiguous product tasks, 2-hour builds) and grading shifts to process: decomposition, prompt specificity, verifying AI output, catching its bugs, narration, ownership of every line. A countervailing block (most Google teams, Apple, Amazon, Netflix, quant, banks, Perplexity's live round, Anthropic's default) still bans AI and relies on multi-part stateful problems instead.

### Cited Findings
- **Meta**: 60 minutes, CoderPad with built-in AI assistant; selectable models (GPT-4o mini, GPT-5, Claude Sonnet 4/4.5, Claude Haiku 3.5/4.5, Gemini 2.5 Pro, Llama 4 Maverick); replaces one of two onsite coding rounds; "A multi-file project you iterate on, rather than two algorithmic problems"; pilot began Oct 2025; author believes AI use being "optional and has no bearing" is "not entirely true" in practice. — [interviewing.io Meta AI-assisted round](https://interviewing.io/blog/how-to-use-ai-in-meta-s-ai-assisted-coding-interview-with-real-prompts-and-examples) **[in-window]**; E6-and-below get one traditional + one AI round, E7+ AI-only; AI "reads files but can't edit" — [ombharatiya compilation](https://github.com/ombharatiya/FAANG-Coding-Interview-Questions/blob/main/AI-Companies-Interview-Questions.md); grading "task breakdown, verification and explanation of AI output rather than hand-coding speed" — [dglearning Substack](https://dglearning.substack.com/p/inside-metas-new-ai-enabled-coding) **[second-hand]**
- **DoorDash**: careers blog (dated Mar 19 2026 per third parties; fetch 403) says it is replacing traditional coding rounds with "a 60-minute, AI-assisted engineering working session"; candidate uses own machine, preferred IDE, "AI tools like Cursor, Claude Code, or Codex"; starter code to modify and debug while explaining; scored on "orientation, AI use and verification, debugging, scope and tradeoffs"; techinterview.org: 60–75 min, "Shipping something that runs; judgment over AI output". — [DoorDash careers blog](https://careersatdoordash.com/blog/doordash-is-rebuilding-its-engineering-interviews-around-ai/); [techinterview.org DoorDash](https://www.techinterview.org/post/3233476844/doordash-software-engineer-interview/?format=md); [aceround DoorDash summary](https://www.aceround.app/blog/doordash-ai-assisted-engineering-interview/) **[in-window]**

### Inferences
- When AI is allowed, companies compensate on three axes: scope (multi-file codebase, 120+ lines, 2-hour builds), ambiguity (product-style tasks needing clarification), and observability (CoderPad/CodeSignal transcripts and replays, screen share, "explain every line"). A pytest-judged mock can approximate the first two by shipping a small starter package with existing tests and a staged feature list; the third needs an interviewer or an AI interviewer pane.
- The AI-allowed and no-AI camps converge on the same *problem shape*: stateful system, requirements that arrive in waves, correctness verified by tests. The difference is whether the candidate types the code.
- The "take-home with AI, then live extension without AI" pattern (HN, Stripe-style, Anthropic perf-eng) is a natural fit for a platform that already hosts timed multi-part problems: part N+1 can be run live after an asynchronous part N.

### Gaps
- Primary statements were not retrievable for DoorDash (403) and Google (Business Insider paywalled); both are reported consistently by multiple secondary outlets.
- No official rubric is published by Meta, DoorDash, Google or Canva; "what graders look for" is from prep sites and interviewer blog posts.
- Reported policies for OpenAI, Stripe, Shopify, Cursor, Glean and Cohere come from a single tracker or compilations without primary links.

## Key Question 4: What separates passing from failing candidates on multi-part problems?

### Takeaway
Across first-hand ICA reports, official guides and interviewer posts, the consistent separators are: (a) reaching and *fully passing* Level 3 (the time/TTL/scheduling level) with earlier tests still green — Level 3 is where most reported candidates stalled, usually on ordering/expiry bugs rather than algorithms; (b) a data model chosen in the first 10–20 minutes that absorbs timestamps and later mutations without rewrite; (c) treating visible/failing tests as the spec and validating before mutating state; (d) in live rounds, narration, clarifying questions, and preserving earlier-part behaviour; (e) in AI-allowed rounds, decomposition before prompting, small verified increments, catching AI bugs, and being able to explain every line.

### Cited Findings
- CodeSignal's design intent: Level 3/4 difficulty "will be dependent on the scalability and reusability of the previous levels"; "an inefficient codebase will be almost impossible to refactor and encapsulate within the time limit"; progress-within-time is "a major factor in assessing candidates' skill levels". — [CodeSignal ICF brief](https://discover.codesignal.com/rs/659-AFH-023/images/Industry-Coding-Skills-Evaluation-Framework-CodeSignal-Skills-Evaluation-Lab-Short.pdf) **[pre-window]**
- Meta bank candidate (first-hand): L1+L2 in ~15 min; "most of the remaining time went to debugging Level 3"; bugs were "small" (expired transfer must refund source; accepted transfer must count toward activity; deposit/pay must behave after expiry) but hard to find in a long 10-account test. — [PracHub Meta bank system](https://prachub.com/interview-experiences/meta-software-engineer-interview-experience-three-of-four-levels-on-the-bank-system-question)
- Airbnb bank candidate (first-hand, 440 pts, presumed fail): did not finish L3; trap is processing due scheduled payments before any later operation. — [PracHub Airbnb banking OA](https://prachub.com/interview-experiences/airbnb-software-engineer-interview-experience-four-level-banking-system-oa-stuck-on-level-3-at-440-points)
- Anthropic coaching: "520 or above generally advances, typically requiring at least 3 of 4 levels fully passing"; "A working but inelegant solution beats an unfinished elegant one"; "If Level 3 exposes a rigid architecture, refactor rather than rewrite"; read all visible tests first. — [Sundeep Teki guide](https://www.sundeepteki.org/advice/anthropic-codesignal-assessment-guide) **[second-hand]**; six-stage update: spend ~20 minutes on a data model "that can absorb unseen requirements" before feature logic; treat failing hidden tests as the real spec; early shortcuts compound across six stages. — [deepsunai Substack](https://deepsunai.substack.com/p/anthropics-codesignal-assessment)
- Airbnb guide advice: rerun earlier tests after each extension; rejected operations leave state unchanged ("Validate before mutating"); choose data structures that make the contract explicit; reduce a failing command sequence to a minimal regression test. — [PracHub Airbnb ICA guide](https://prachub.com/resources/airbnb-codesignal-industry-coding-assessment-2027-four-levels-90-minutes-scoring-and-what-comes-next)
- Perplexity (official): main signal is "high-quality work that correctly and precisely meets the requirements"; also "methodical approach to problem solving and debugging", "technical judgment (abstractions, code quality, tradeoffs)", "precise, efficient execution"; "Solving all parts is not required"; "make as much progress as you can without becoming sloppy or careless"; evaluators look for "Preserving Part 2 behavior as the design changes" and "Code that is easy to explain, test, and extend". — [Perplexity format](https://interviewresources.perplexity.ai/hands-on-coding/); [Perplexity todo example](https://interviewresources.perplexity.ai/hands-on-coding/examples/todo-list/) **[first-party]**; one rejected candidate cited a "timeout on large test case" — [PracHub Perplexity experience](https://prachub.com/interview-experiences/perplexity-software-engineer-interview-experience-a-4-part-todo-list-for-ai-coding-round)
- Anthropic live coding grading: "Justification of complexity choices, edge-case handling under pressure, reading ambiguous specs, and reasoning behind decisions"; one engineer described the take-home as "a black-box evaluator, with the spec's details learned mainly by running code and seeing which tests fail"; "Candidates often run out of time, so time management matters." — [interviewing.io Anthropic](https://interviewing.io/anthropic-interview-questions)
- OpenAI reports: "A working solution first, then optimization, since interviewers often add requirements"; clarify and outline before coding; explicit empty/null/boundary handling; "Production-ready code: clear names, helper functions"; candidates "spent the full hour typing". — [Hello Interview OpenAI](https://www.hellointerview.com/blog/openai-coding-questions) **[second-hand]**
- Meta AI round pass signals: plan before prompting; specific contextual prompts; small iterative changes validated each time; catching bugs/missing edge cases in AI output and explaining fixes; narrating what was asked and why; simplifying convoluted AI code; hand-writing when faster. Fail signals: accepting output without understanding; letting AI design the whole solution; cannot explain code; over-tuning prompts; using AI for trivial tasks. — [interviewing.io Meta AI-assisted round](https://interviewing.io/blog/how-to-use-ai-in-meta-s-ai-assisted-coding-interview-with-real-prompts-and-examples)
- Canva: strongest candidates "asked clarifying questions, used AI for well-defined subtasks, reviewed and improved AI output, and debugged effectively"; graded on breaking down ambiguous requirements, sound decisions, finding/fixing issues in AI code, production standards; "we're more interested in seeing strong engineering fundamentals amplified by AI tools". — [Canva blog](https://canva.dev/blog/engineering/yes-you-can-use-ai-in-our-interviews); [Canva follow-up](https://www.canva.dev/blog/engineering/ai-interview-success/)
- Sierra Review grades data model, abstractions, extensibility, path to production, product choices, AI usage; criteria "agnostic to what the candidate builds". — [Sierra blog](https://sierra.ai/blog/the-ai-native-interview)
- HN interviewers: weak candidates "cannot actually break down the problem even verbally"; red flags: not finding any planted errors, making assumptions and "double down on building the wrong thing", one-shotting a whole ticket into Claude; good: clarifying questions, pushback on bad requirements, deliberate steering, "Judge them on quality of the output first." — [Ask HN thread](https://news.ycombinator.com/item?id=49768826) **[in-window, first-hand]**
- Stripe graders: "Production-quality code that 'actually runs,' with trade-offs discussed as in a real pull request"; asking clarifying questions and "committing to a direction with calibrated confidence"; written communication via short memo/bug report. — [techinterview.org Stripe](https://www.techinterview.org/companies/stripe/) **[second-hand]**
- Meta OA: a Glassdoor review reports advancing after ~50% of tasks solved. — [copilotinterview Meta OA](https://copilotinterview.com/blog/meta-online-assessment) **[second-hand]**
- Community mock shows the hazard of test/spec mismatch: candidates who implemented a "correct" destructive rollback failed the mock's tests; only non-destructive behaviour passed. — [GitHub issue #16](https://github.com/PaulLockett/CodeSignal_Practice_Industry_Coding_Framework/issues/16)

### Inferences
- For a pytest-judged platform, the most diagnostic tests are regression tests on earlier levels after a later level is implemented (both Airbnb's guide and the Meta candidate's "top-N test fails after accept" bug point here), and boundary tests on time (exactly-at-expiry, due-at-this-timestamp, expired-then-accepted).
- Grading weights that mirror the reports: Level 3 fully green ≈ pass line for ICA-style 90-minute problems; partial Level 3 with Levels 1–2 green ≈ borderline (Airbnb 440/600 presumed fail; Meta Glassdoor "50%" pass suggests company cutoffs differ).
- Narration and clarification are only measurable with an interviewer (human or AI pane); a platform can proxy "extensibility" with a hidden Level-4 regression suite and by timing how long Level 3 took relative to Levels 1–2.

### Gaps
- No company publishes a rubric; the 520/600 and "3 of 4 levels" claims are from one coaching source and could not be cross-checked against an official cutoff.
- No controlled data compares pass rates by level reached; all evidence is anecdotal (single candidates, coaching clients, an HN thread with ~43 comments).
- The Meta Glassdoor "50%" datum is second-hand via a prep site; I did not retrieve the review itself.
