## Key question 1: What exact coding problems (with parts) did Decagon ask?

### Takeaway
Decagon's 2026 loop is dominated by a small, repeating set of "practical OOD" multi-part problems: a Cooking-App Recipe Shopping Cart (discounts, then undo/redo or versioning/checkout, then nested transactions), a Rolling CSAT Tracker (window average, then updates, then percentile), Count Legal Tic-Tac-Toe Games (3x3 backtracking, with a 4x4 three-in-a-row variant), Batch API Requests with Per-Request Retry Delays, and Exclusive CPU Time from Nested Logs. Design screens are "data modeling" prompts (AI-agent rule management with drafts/publish/rollback; delayed job scheduler; chatbot security) and the onsite design is a multi-tenant AI Gateway.

Problem A — Cooking-app Recipe Shopping Cart (phone screen; the most-reported Decagon problem)
- FIRST-HAND, SWE technical screen, July 2026 (published 2026-08-24), rated Hard, rejected despite finishing both problems. Statement as reported: "You're building a shopping cart for a cooking app. Users add recipes to the cart, and each recipe has a list of ingredients. When an ingredient appears in multiple recipes, the total count qualifies for bulk discounts." Part 1: implement `add_recipe`, `remove_recipe`, `get_total_discounts`. Part 2: add `checkout` and `get_version`; every cart operation creates a new version; checking out an older version discards all newer versions (after add A = v1, add B = v2, `checkout(1)` discards v2). Interviewer required a space-efficient design: candidate switched from storing full snapshots to storing only (add, x)/(remove, x) operations and replaying up to the requested version, plus a `_discard_future_versions` helper. Round 1 interviewer "very friendly and gave many hints" — [PracHub experience](https://prachub.com/interview-experiences/decagon-software-engineer-interview-experience-shopping-cart-versioning-then-rejected-on-tic-tac-toe)
- Undo/redo variant: FIRST-HAND Sep 2026 phone screen "a shopping cart problem that required implementing redo and undo" — [PracHub experience](https://prachub.com/interview-experiences/decagon-software-engineer-interview-experience-rejected-after-the-onsite-culture-screen); 1point3acres summary for the 2026-06-18 report: "common cooking app cart system coding interview, including recipe management and undo/redo functionality" — [thread 1180593](https://www.1point3acres.com/interview/thread/1180593); PracHub question bank lists "Shopping Cart with Undo and Redo for Add and Remove Operations" (Medium, listed 2026-09-18, locked) — [PracHub Decagon](https://prachub.com/companies/decagon)
- Nested-transaction variant: PracHub lists "Add Nested Begin, Commit, and Abort Semantics to a Shopping Cart" (Hard, 2026-07-13, locked; "comparing snapshot and undo approaches") — [PracHub Decagon](https://prachub.com/companies/decagon). FastPrep RECONSTRUCTED version ("judged core matches the combined reports at about 90%"; finite bounds and batch interface are practice choices): operations `add_recipe`, `remove_recipe`, `get_total_discount`, `begin`, `commit`, `abort`; discount queries see uncommitted changes; outer abort reverses inner commits; inner abort keeps earlier outer changes; commit/abort with no open scope is a no-op; depth <= 100; discount rule = per ingredient, the highest tier whose threshold <= current count, amount counted once, summed across ingredients — [FastPrep Nested Recipe Cart Transactions](https://www.fastprep.io/problems/decagon-nested-recipe-cart-transactions)

Problem B — Rolling CSAT (customer-satisfaction) Tracker (phone screen; also onsite per FastPrep)
- FIRST-HAND, SWE phone screen, April 2026 (published 2026-08-25), 45 minutes, passed. Base: class with `__init__(window_size)`, `record(conversation_id, score, timestamp)` (scores 1–5, timestamps strictly increasing), `get_average(current_time)` -> average of scores in the active window rounded to 2 dp. Follow-up 1: `update(conversation_id, score)` changes the score only if the conversation is still in the window (expired -> no-op; original timestamp/order unchanged). Follow-up 2: given `p`, return the score at that percentile (p50 = median). Candidate wrote two bugs, caught both while testing — [PracHub experience](https://prachub.com/interview-experiences/decagon-software-engineer-interview-experience-csat-tracker-question-on-the-phone-screen)
- PracHub question page (Easy; formalised version): active iff `current_time - timestamp <= window_size`; `get_average` returns 0.0 if none active; `get_percentile(current_time, p)` uses nearest-rank index `ceil(p/100*n)-1`, None if none active; constraints window_size <= 1e9, up to 2e5 operations; hints: queue for expiry, score-frequency counts (scores 1–5) for percentiles — [PracHub CSAT tracker](https://prachub.com/coding-questions/implement-a-csat-sliding-window-tracker)
- FastPrep: "Rolling CSAT Tracker", Medium, Phone and Onsite, 10 public reports, last reported Nov 2026 (the most-reported Decagon problem in that catalog); related "Count Hits in the Last Five Minutes" (1 report, Apr 2026) — [FastPrep Decagon](https://www.fastprep.io/decagon-interview). ### Inferences
- The phone screen is typically two problems in ~45 minutes: a stateful OOD class (cart or CSAT tracker) with 2–3 escalating parts, then a counting/backtracking problem (tic-tac-toe) — consistent across the Jul 2026 first-hand report and the FastPrep/PracHub catalogs.

- Rejections after completing both problems (Jul 2026) and after a culture screen (Sep 2026) suggest the bar is on code quality/space-efficiency and culture fit, not just finishing.

## Key question 2: What exact coding problems (with parts) did Mercor ask?

### Takeaway
Mercor's 2026 SWE loop is a ~30-minute spoken "no-code" phone screen (worst/fastest sorting algorithm, a coffee-ranking probability puzzle, live code review of a CSV builder, a threaded memoization cache and a charge-then-record payment method) followed by an in-person SF onsite (noon–5pm) with a three-part screen-recorded coding round (a "referral network" problem), a spoken algorithms round (sort/top-k with a noisy comparator; friend-network exploration via a restricted API; currency conversion), a whiteboard system design (job scheduler / workflow orchestration) and a 90-minute "candidate search" build against an evaluation endpoint with LLMs allowed.

## Key question 6: What distinguishes passing candidates according to reports?

### Takeaway
Reports converge on: state complexity and space-efficiency unprompted (Decagon), answer every rapid-fire question briefly and go beyond style in code review (Mercor), ship executable end-to-end code and show low-level design in the timed build (Glean), and be able to defend every line of AI-generated code where AI is allowed (Mercor).
